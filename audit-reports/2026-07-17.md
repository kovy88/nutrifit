# Daily audit — 2026-07-17

## Implementovaný task

**Logovat network/API chyby v health providerech místo tichého `[]`/`null`** (Quick wins) — commit `5b3e796`.

### Co se změnilo

Oura, Strava i Whoop provider polykaly každou chybu fetche a vracely `[]`/`null`. `CompositeHealthDataProvider` to nedokáže odlišit od „uživatel ten den prostě nic nenaměřil", takže odvolaný token nebo výpadek providera byl neviditelný, dokud si uživatel sám nevšiml, že se mu data přestala synchronizovat.

Přidán `console.warn` před každý spolknutý fail, ve všech třech providerech, na třech místech:

- **network throw** (`fetch` hodí) → `…: <endpoint> request failed`, včetně chybového objektu
- **non-OK status** (401/429/500/503…) → `…: <endpoint> returned HTTP <status>` — status kód je v hlášce, takže z logu jde poznat expirovaný token (401) od rate limitu (429) a výpadku (5xx)
- **nečitelné tělo odpovědi** → `…: <endpoint> returned an unreadable body`
- **selhaný token refresh** → `…: token refresh failed — user needs to reconnect <provider>`

**Návratové hodnoty ani signatury se nezměnily** — je to čistě přidaná viditelnost, žádná změna chování.

### Dvě rozhodnutí, která se liší od zadání v plánu

1. **Chybějící token se záměrně neloguje.** Plán říkal „logovat před return prázdné hodnoty", ale `!token` je normální „uživatel nemá připojeno" stav — platí pro každého uživatele bez Oury/Whoopu/Stravy. Logovat ho by utopilo reálné chyby v šumu. Logováno je místo toho **selhání refreshe**, což je přesně ten neviditelný případ, kvůli kterému task vznikl.
2. **Prefix `OuraProvider: …` místo navrhovaného `[OuraProvider]`.** Kód už má zavedenou konvenci `Modul: zpráva` (`api.ts`, `ThemeContext.tsx`, `useDailyCoaching.ts`, `HistoryScreen.tsx`) — držel jsem se jí.

Bez `__DEV__` guardu (na rozdíl od `useDailyCoaching.ts`), protože přínos uvedený v plánu je explicitně viditelnost v **produkčních** logech.
