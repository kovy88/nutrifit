## Task 1 — Logovat network/API chyby v health providerech místo tichého `[]`/`null`

Commit `5b3e796` (Quick wins).

### Co se změnilo

Oura, Strava i Whoop provider polykaly každou chybu fetche a vracely `[]`/`null`. `CompositeHealthDataProvider` to nedokáže odlišit od „uživatel ten den prostě nic nenaměřil", takže odvolaný token nebo výpadek providera byl neviditelný, dokud si uživatel sám nevšiml, že se mu data přestala synchronizovat.

Přidán `console.warn` před každý spolknutý fail, ve všech třech providerech, na třech místech:

- **network throw** (`fetch` hodí) → `…: <endpoint> request failed`, včetně chybového objektu
- **non-OK status** (401/429/500/503…) → `…: <endpoint> returned HTTP <status>` — status kód je v hlášce, takže z logu jde poznat expirovaný token (401) od rate limitu (429) a výpadku (5xx)
- **nečitelné tělo odpovědi** → `…: <endpoint> returned an unreadable body`
- **selhaný token refresh** → `…: token refresh failed — user needs to reconnect <provider>`

**Návratové hodnoty ani signatury se nezměnily** — je to čistě přidaná viditelnost, žádná změna chování.

### Dvě rozhodnutí, která se liší od zadání v plánu

1. **Chybějící token se záměrně neloguje.** Plán říkal „logovat před return prázdné hodnoty", ale `!token` je normální „uživatel nemá připojeno" stav — platí pro každého uživatele bez Oury/Whoopu/Stravy. Logovat ho by utopilo reálné chyby v šumu. Logováno je místo toho **selhání refreshe**, což je přesně ten neviditelný případ, kvůli kterému task vznikl.
2. **Prefix `OuraProvider: …` místo navrhovaného `[OuraProvider]`.** Kód už má zavedenou konvenci `Modul: zpráva` (`api.ts`, `ThemeContext.tsx`, `useDailyCoaching.ts`, `HistoryScreen.tsx`) — držel jsem se jí.

Bez `__DEV__` guardu (na rozdíl od `useDailyCoaching.ts`), protože přínos uvedený v plánu je explicitně viditelnost v **produkčních** logech.

### Dvě rozhodnutí, která stojí za zmínku

1. **Stripe podpisy se nemockují.** Testy podepisují payload **skutečným** Stripe SDK (`generateTestHeaderString`), takže `constructEvent` v handleru ověřuje doopravdy — celé to funguje offline. Mockovaný podpis by z nejdůležitějšího testu v souboru udělal atrapu, která projde i nad rozbitým ověřením. Stubuje se jen Stripe *API* (`checkout.sessions.list`, `billingPortal.sessions.create`, `customers.list`) — přes injektáž továrny do `require.cache`, která nechá objekt `webhooks` skutečný.
2. **`tests/run.js` není potřeba měnit.** Plán zmiňoval možný update kvůli objevení nových souborů, ale `readdirSync` si `*.test.js` najde sám.

## Dva nové nálezy (přidány do plánu jako tasky)

**1. `export const config` ve `stripe-webhook.js` se zahazuje.** Řádek 7 nastaví `module.exports.config = { api: { bodyParser: false } }`, řádek 22 pak `module.exports` celý přepíše funkcí handleru. Ověřeno spuštěním: `require('./api/stripe-webhook.js').config` je `undefined` — ta konfigurace se k Vercelu nikdy nedostane. Navíc `config.api.bodyParser` je konvence **Next.js API Routes** a tenhle repozitář Next.js nemá, takže jde o čisté Vercel serverless funkce, kde ten klíč nejspíš stejně nic neznamená. Buď je to mrtvý matoucí kód, nebo webhook běží na štěstí. **Neopravoval jsem to** — přesun `config` za přiřazení by ho poprvé reálně aktivoval, a to je změna chování produkčního webhooku naslepo. Chce to napřed potvrdit z produkčních logů, že aktivace premia reálně prochází.

**2. `tests/run.js` nečeká na async testy.** Vrácený promise se nikde neawaituje, takže async testy v jednom souboru běží souběžně. Dosud neškodilo (doménové testy nesdílí stav), ale nové api testy sahají na `globalThis.fetch` a `process.env` — bez `await test(...)` si navzájem přepisovaly mocky (narazil jsem na to, první běh padal na cizí fetch mock). Vyřešeno `await test(...)` v nových souborech + varováním v hlavičce harnessu; správná oprava (fronta v `run.js`) je teď v Quick wins.
